AI 시대의 도메인 지식 · 온톨로지 · DDD

도메인이란 무엇인가

도메인은 AI나 소프트웨어가 다루는 현실 세계의 문제 영역이고, 온톨로지는 그 세계의 객체·관계·규칙을 AI가 따라갈 수 있게 만든 의미 지도다.

작성자 Hermes 작성 2026-05-01 수정 2026-05-05 status active
Executive Summary

기술은 “어떻게”, 도메인은 “무엇과 왜”를 정한다

도메인은 AI가 일할 현실 세계의 지도이고, 온톨로지는 그 지도 안의 객체·관계·제약을 연결한 업무 관계도다.

기술이 “어떻게 만들 것인가”라면, 도메인은 “무엇을 만들고 그 세계가 어떤 용어와 규칙으로 돌아가는가”를 뜻한다. 온톨로지는 여기서 한 걸음 더 나아가 “그 용어들이 서로 어떻게 연결되는가”를 구조화한다.
Why Now

AI는 빠르게 만들지만, 현실의 의미는 자동으로 맞히지 못한다

AI에게 “주문 기능 만들어줘”라고 말하면 일반적인 쇼핑몰을 떠올려 Order, Payment, Cart, Checkout을 만들 수 있다. 하지만 회사마다 “주문”의 의미는 다르다.

같은 단어, 다른 업무

  • 어떤 회사에서 주문은 결제 전 예약 상태다.
  • 어떤 회사에서 주문은 결제 완료 후 거래다.
  • 어떤 회사에서는 물류 출고 요청까지 포함한다.
  • 어떤 회사에서는 결제 실패 주문도 기록에 남긴다.

의미가 달라지면 구조도 달라진다

  • 데이터 구조
  • 상태 흐름
  • 예외 처리
  • 환불 로직
  • 재고 차감 시점
AI 시대에는 “코드를 얼마나 빨리 만들 수 있느냐”보다 “AI에게 맡길 문제 세계를 얼마나 정확히 설명할 수 있느냐”가 중요해진다.
Definition

도메인은 업계 사람들이 당연하게 아는 세계다

도메인 = 우리가 해결하려는 현실 세계의 문제 영역

도메인 지식 = 그 세계가 실제로 돌아가는 규칙과 경험

도메인 언어 = 그 세계 사람들이 쓰는 정확한 용어

도메인 모델 = 그 용어와 규칙을 소프트웨어·문서·AI 작업 구조로 정리한 것

온톨로지 = 그 세계의 개념, 속성, 관계, 제약을 기계가 따라갈 수 있게 연결한 의미 지도

구분 예시 핵심 질문
기술 영역 React, Next.js, Python, API, DB, CSS, Docker 어떻게 만들 것인가?
도메인 영역 주문, 결제, 환불, 진료, 처방, 인박스, 원문, 요약 무엇을 만들고 어떤 의미인가?
데이터 영역 테이블, 컬럼, JSON, 로그, 벡터, 파일 무엇을 저장하고 조회할 것인가?
운영 영역 승인, 배포, 검증, 장애 대응, 권한 어떻게 안전하게 굴릴 것인가?

기술은 도구다. 도메인은 그 도구로 해결하려는 현실이다.

Ontology

온톨로지는 단어 목록이 아니라 업무 세계의 연결 구조다

쇼핑몰 도메인에는 고객, 상품, 장바구니, 주문, 결제, 배송, 환불이 있다. 여기까지는 용어집이다. 온톨로지는 이 개념들이 어떻게 이어지는지까지 말한다.

관계 예시

  • 고객은 주문을 생성한다.
  • 주문은 주문 항목을 포함한다.
  • 주문 항목은 상품을 참조한다.
  • 주문은 결제와 연결된다.
  • 결제 성공 후에만 주문이 확정된다.

개념 쉬운 설명 산출물
도메인 해결하려는 현실 세계 커머스 주문·환불 업무
도메인 지식 그 세계의 규칙과 예외 결제 성공 전에는 주문 확정 아님
도메인 언어 사람들이 같이 쓰는 정확한 단어 주문, 결제, 배송, 환불
도메인 모델 코드나 문서로 옮긴 업무 구조 Order, Payment, Refund
온톨로지 객체·속성·관계·제약의 의미 지도 Customer - places - Order
지식 그래프 온톨로지에 실제 데이터를 채운 연결망 성배 - placed - 주문123
핵심: 도메인 문서가 “업무 매뉴얼”이라면, 온톨로지는 “업무 관계도”다. AI 에이전트가 안정적으로 움직이려면 매뉴얼과 관계도가 함께 필요하다.
Five Contexts

“도메인”은 다섯 가지 맥락에서 쓰인다

1. 비즈니스 도메인

쇼핑몰, 병원, 금융, 교육, 물류, 통신, 제조처럼 소프트웨어가 다루는 업무 영역이다. 통신 영업 도메인이라면 요금제, 약정, 해지, 번호 이동, 부가서비스, 단말기 할부, 고객 등급, 계약 조건, 현장 영업 프로세스가 중요하다.

2. 도메인 지식

문서에 깔끔하게 적히지 않은 현장 지식까지 포함한다. 고객이 헷갈리는 포인트, 늘 생기는 예외, 법과 규제, 내부 은어, 실패 사례, 경험칙이 여기에 들어간다.

3. 도메인 언어

DDD의 Ubiquitous Language다. 개발자와 도메인 전문가가 함께 쓰는 공통적이고 엄격한 언어이며, 코드·문서·테스트·프롬프트에 일관되게 반영되어야 한다.

4. 도메인 특화 언어, DSL

SQL, HTML/CSS, Terraform, Mermaid, 정규식처럼 특정 문제 영역을 위해 만든 언어다. AI에게는 문법, 좋은 예시, anti-pattern, 검증 루프가 함께 필요하다.

5. 온톨로지와 지식 그래프

AI 에이전트, Graph RAG, 기업 자동화에서 중요해진 맥락이다. 업무는 문장만으로 돌아가지 않고 객체, 상태, 관계, 권한, 액션, 예외로 움직인다.

DDD

DDD는 실제 비즈니스 세계의 개념과 언어를 코드 구조에 드러내는 태도다

“코드를 기술 중심으로만 짜지 말고, 실제 비즈니스 세계의 개념과 언어가 코드 구조에 드러나게 하자.”

DDD의 핵심은 복잡한 패턴 이름을 외우는 것이 아니다. 중요한 것은 도메인 전문가와 개발자가 같은 언어를 쓰고, 그 언어가 코드, 문서, 테스트, AI 프롬프트에도 일관되게 반영되는 것이다.

개념 쉬운 설명 예시
Domain 해결하려는 문제 세계 쇼핑몰, 병원 예약, LLM Wiki
Domain Knowledge 그 세계가 돌아가는 규칙 결제 성공 시점에만 재고 차감
Ubiquitous Language 모두가 같이 쓰는 정확한 용어 주문, 체크아웃, 결제, 환불을 구분
Domain Model 규칙과 용어를 구조로 만든 것 Order, Payment, Refund, Inventory
Ontology 개념과 관계를 기계가 따라가게 만든 의미 지도 Customer가 Order를 만들고 Order가 Payment를 가진다
Bounded Context 같은 단어가 같은 의미로 쓰이는 경계 물류의 Product와 판매의 Product는 다를 수 있음
Entity 고유한 ID가 중요한 객체 고객, 주문, 계좌
Value Object 값 자체가 중요한 객체 주소, 금액, 기간
Aggregate 일관성을 지키는 객체 묶음 주문과 주문 항목
Domain Event 도메인에서 일어난 의미 있는 사건 주문 완료됨, 결제 실패함, 노트 발행됨
Language Boundary

같은 단어도 팀마다 다른 의미를 갖는다

“상품”이라는 단어도 판매팀, 물류팀, 회계팀, CS팀, 마케팅팀에서 서로 다른 규칙을 가진다. 이 경계를 나누지 않으면 AI는 판매 로직, 물류 로직, 회계 로직을 한 클래스나 한 프롬프트 안에 섞어버릴 수 있다.

문맥 상품의 의미
판매팀 고객에게 판매되는 상품명, 가격, 프로모션
물류팀 창고에서 피킹·포장·출고되는 물리적 재고
회계팀 매출 인식과 세금 처리를 위한 항목
CS팀 교환·반품·환불 정책이 적용되는 대상
마케팅팀 캠페인, 타깃, 노출 소재와 연결되는 단위
Bounded Context는 같은 단어가 같은 의미로 통하는 범위다. 이 범위를 벗어나면 같은 단어라도 새로 정의해야 한다.
Failure Modes

AI가 도메인을 모르면 그럴듯하지만 어긋난 결과가 나온다

  1. 단어를 섞는다. Order, Checkout, Purchase, Payment를 비슷한 뜻으로 섞어 쓴다.
  2. 현실 규칙을 놓친다. 결제 취소, 부분 환불, 반품 완료 후 환불, 포인트 환급의 차이를 무시할 수 있다.
  3. 검증 기준이 없다. “완료했습니다”라는 말만 보고 실제 DB에 booking이 생성됐는지 확인하지 않을 수 있다.
  4. 맥락이 너무 많아져도 망가진다. 현재 작업에 필요한 정확한 컨텍스트가 아니라 모든 문서를 넣으면 context rot이 생긴다.
  5. 관계를 따라가지 못한다. VIP 고객의 환불 승인처럼 고객, 주문, 결제, 반품, 권한, 정산 관계를 따라가야 하는 일을 즉석에서 추측한다.
도메인 용어만 알려줘도 AI는 어느 정도 답할 수 있다. 그러나 업무가 복잡해지면 단어보다 관계가 중요해진다.
AI Work Context

AI 시대의 도메인은 “AI에게 주는 작업 세계 설명서”다

GPT 프롬프트가 결과 계약서에 가깝다면, 도메인은 그 계약서의 업무 세계다. 좋은 AI 작업에는 작업 계약서, 도메인 설명서, 온톨로지 초안이 함께 있어야 한다.

요소 역할
결과 계약서 무엇이 끝난 상태인가?
도메인 그 결과가 어떤 현실 세계 규칙 안에서 의미를 갖는가?
도메인 언어 그 세계를 어떤 단어로 정확히 부를 것인가?
도메인 모델 그 단어와 규칙을 어떤 구조로 표현할 것인가?
온톨로지 그 구조 안의 객체들이 서로 어떤 관계를 맺는가?
검증 기준 현실 세계에서 정말 성공했는지 어떻게 확인할 것인가?

1. 작업 계약서

목표, 성공 기준, 제약, 출력 형식, 멈춤 조건

2. 도메인 설명서

용어, 상태, 규칙, 예외, 예시, 검증 방법

3. 온톨로지 초안

핵심 객체, 속성, 관계, 제약, 가능한 액션

Analogy

AI는 똑똑한 신입이고, 도메인은 회사 업무 매뉴얼이다

AI는 문서 작성도 잘하고, 코드도 빨리 짜고, 검색도 빠르다. 하지만 입사 첫날에는 우리 회사의 업무 규칙을 모른다.

도메인 문서가 알려주는 것

  • 무엇을 같은 것으로 봐야 하는가
  • 무엇을 다르게 봐야 하는가
  • 어떤 단어를 쓰고 쓰지 말아야 하는가
  • 어떤 상태 전이가 가능한가
  • 어떤 예외가 중요한가
  • 어떤 결과가 진짜 완료인가

온톨로지가 추가로 알려주는 것

  • 고객은 계약자와 사용자를 모두 포함하는가
  • 계약자는 여러 회선을 가질 수 있는가
  • 회선은 요금제, 약정, 부가서비스와 어떻게 연결되는가
  • 상담원과 승인자가 바꿀 수 있는 객체는 무엇인가
Example Domain

LLM Wiki / Obsidian 볼트도 하나의 도메인이다

이 볼트에는 기술보다 중요한 업무 언어가 있다. AI가 이 도메인을 모르면 원문 보존 원칙을 깨거나, 인박스와 위키 컴파일을 같은 작업처럼 처리할 수 있다.

Document Design

도메인 문서는 길이보다 구조가 중요하다

1. 도메인 범위

이 시스템이 다루는 문제와 다루지 않는 문제를 적는다.

2. 용어집

같은 개념은 같은 단어로, 다른 개념은 다른 단어로 정의한다.

3. 온톨로지 초안

핵심 객체와 관계를 triple 형태로 적는다.

4. 상태와 생명주기

상태가 있는 도메인이라면 가능한 흐름과 불가능한 전이를 적는다.

5. 규칙과 불변 조건

절대 깨지면 안 되는 업무 규칙을 명시한다.

6. 예시와 반례

좋은 예시뿐 아니라 나쁜 예시도 함께 제공한다.

7. 검증 방법

AI가 말로 완료했다고 해서 끝내지 말고 실제 도메인 결과를 확인한다.

예시 코드 블록 보기 
## Domain Scope

# Domain Brief

## 1. Domain Scope
이 프로젝트가 해결하는 현실 세계 문제는 무엇인가?
다루지 않는 범위는 무엇인가?

## 2. Users / Actors
이 도메인에 등장하는 사람 또는 시스템은 누구인가?
각자의 목표는 무엇인가?

## 3. Glossary
핵심 용어를 정의한다.
같은 단어를 여러 의미로 쓰지 않는다.
다른 의미는 다른 단어로 분리한다.

## 4. Lifecycle / State
중요 객체의 상태 흐름을 적는다.
어떤 상태 전이가 가능한지/불가능한지 적는다.

## 5. Ontology Sketch
핵심 객체, 속성, 관계를 적는다.
객체 간 관계를 triple 형태로 10개 안팎 작성한다.

## 6. Business Rules
반드시 지켜야 하는 규칙을 적는다.
규칙의 이유도 짧게 적는다.

## 7. Examples / Anti-examples
좋은 예시와 나쁜 예시를 각각 3~5개 적는다.

## 8. Tool / Validation Rules
AI가 언제 도구를 써야 하는지,
무엇을 확인하면 완료인지 적는다.

## 9. Output / Naming Rules
코드, 문서, 응답에서 어떤 이름과 형식을 쓸지 정한다.
Domain Expertise

도메인을 안다는 것은 업계 단어를 많이 아는 것이 아니다

도메인을 안다는 것은 객체, 상태, 관계, 제약, 예외, 완료 기준, 고객 가치, 자동화 위험을 설명할 수 있다는 뜻이다.

도메인 전문가가 답해야 할 질문

  • 이 일에서 진짜 중요한 객체는 무엇인가?
  • 이 객체는 어떤 상태를 가지는가?
  • 다른 객체와 어떤 관계를 맺는가?
  • 가능한 상태 전이와 불가능한 전이는 무엇인가?
  • 반드시 지켜야 하는 규칙과 예외는 무엇인가?

AI 시대의 확장 역량

  • 무엇이 실제 완료인지 정의한다.
  • 어떤 결과가 고객에게 가치 있는지 판단한다.
  • 어떤 자동화가 위험한지 구분한다.
  • 어떤 검증을 통과해야 믿을 수 있는지 정한다.
  • 객체 간 관계를 구조화해 온톨로지로 만든다.
Misunderstandings

흔한 오해 네 가지

오해 1. 도메인 = 업종 이름이다

“금융”이나 “교육”은 너무 크다. 실제로 필요한 것은 “개인 대출 심사”, “사내 AI 입문 강의 운영”, “반품 승인과 환불 처리”처럼 좁은 문제 세계다.

오해 2. 도메인 지식은 현업만 가진다

현업이 가장 많이 알지만, 개발자도 도메인 지식을 가져야 한다. 현업도 AI와 소프트웨어가 이해할 수 있게 지식을 구조화해야 한다.

오해 3. 도메인 문서는 길수록 좋다

좋은 도메인 문서는 짧더라도 핵심 용어, 객체와 관계, 상태 흐름, 규칙, 예외, 예시, 검증 기준이 분명하다.

오해 4. DDD는 대규모 백엔드에만 필요하다

전통적인 DDD 패턴 전체는 복잡한 시스템에서 더 필요하지만, 도메인 언어와 bounded context는 작은 AI 작업에도 필요하다.

Practical Checklist

AI에게 일을 맡기기 전 10분 도메인·온톨로지 정리

  1. 이 작업의 도메인은 무엇인가?
  2. 핵심 용어 10개는 무엇인가?
  3. 헷갈리기 쉬운 비슷한 단어는 무엇인가?
  4. 핵심 객체 5~10개는 무엇인가?
  5. 객체 간 관계 10개는 무엇인가?
  6. 반드시 지켜야 하는 규칙 5개는 무엇인가?
  7. 상태 흐름이 있는가?
  8. 예외 상황은 무엇인가?
  9. 좋은 결과 예시는 무엇인가?
  10. 나쁜 결과 예시는 무엇인가?
  11. AI가 어떤 도구나 파일을 확인해야 하는가?
  12. 무엇을 확인하면 완료라고 볼 수 있는가?
특히 4번과 5번이 온톨로지의 시작이다. 객체와 관계를 적는 순간 AI는 문장을 생성하는 수준에서 업무 세계를 따라가는 수준으로 올라간다.
Prompt Architecture

GPT-5.5 프롬프트는 Outcome Contract와 Domain Brief를 분리하면 강해진다

A. Outcome Contract

목표: 무엇을 끝낼 것인가
성공 기준: 어떤 조건을 만족하면 완료인가
제약: 하지 말아야 할 것
출력 형식: 어떤 형태로 답할 것인가
Stop rules: 언제 검색/도구/질문을 멈출 것인가

B. Domain Brief

도메인 범위: 어떤 문제 세계인가
용어집: 핵심 단어와 의미
온톨로지 초안: 핵심 객체와 관계
상태 흐름: 중요한 객체의 생명주기
규칙: 반드시 지켜야 할 업무 조건
예시/반례: 좋은 것과 나쁜 것
검증: 실제 성공 여부를 어떻게 확인할 것인가

둘을 합치면 AI에게 “무엇을 만들지”와 “그 일이 어떤 세계에서 의미를 갖는지”가 동시에 전달된다.

Key Insights

핵심 인사이트

  1. 도메인은 AI가 일할 현실 세계의 지도다. 지도 없이 AI에게 일을 시키면 일반론으로 빠진다.
  2. 도메인 언어는 AI와 사람이 공유하는 업무 사전이다. 같은 단어를 같은 의미로 쓰게 만드는 것이 품질의 시작이다.
  3. 도메인 지식은 AI의 오작동을 막는 필터다. 현장 규칙과 예외를 모르면 그럴듯하게 틀릴 수 있다.
  4. 온톨로지는 AI가 관계를 따라가게 만드는 업무 지도다. 객체와 관계가 없으면 단어는 맞혀도 업무 연결을 틀릴 수 있다.
  5. 도메인 문서는 프롬프트의 확장이다. AGENTS.md, CLAUDE.md, skills, glossary, 온톨로지, 테스트 시나리오가 모두 도메인 컨텍스트다.
  6. AI 시대의 경쟁력은 기술 사용 능력 × 도메인 해석 능력 × 관계 구조화 능력이다. 코딩 속도보다 문제 정의, 관계 설계, 검증 기준이 더 중요해진다.
